# Core Runtime Review — Findings
# Files reviewed: llm.py, agent_runtime.py, mini_agent.py, stream.py, retry.py, prompt.py

======================================================================
llm.py
======================================================================

[HIGH] llm.py:~440–450 — Race condition on `recent_tool_keys` in deferred stream results path.
  In the `_on_tool_ready` callback, tool results are appended to `recent_tool_keys` WITHOUT
  holding `tool_keys_lock`. Since `_on_tool_ready` is called from the single-threaded stream
  parser, this is currently safe, but the code is misleading: `_append_tool_result` accepts
  a `lock` parameter, yet the deferred-results append at lines 435–447 calls it without the
  lock. If parallel streaming is ever introduced, this will break silently.

[HIGH] llm.py:~640–645 — `run_agent_turn` may return `msg` undefined when max_turns=0.
  At the end of the function, `return msg` is called after the for-loop exhausts. If
  `max_turns` were 0 (e.g. due to a future bug or config error), `msg` is never assigned
  and the function would raise `UnboundLocalError`. Add a guard: `if 'msg' not in locals()`.

[HIGH] llm.py:~305–325 — `_MODIFIED_FILES` is a module-level mutable set shared across
  parallel tool executions without any locking. Multiple threads in the parallel tool
  execution path (ThreadPoolExecutor) can write to `_MODIFIED_FILES` simultaneously
  via `write_file` / `edit_file`, corrupting the set. Either use a threading.Lock or
  switch to a thread-safe data structure.

[MED] llm.py:~265 — Silent exception swallowing for git diff.
  `except Exception: pass` silently drops all errors from the `git diff` subprocess call.
  If git is not installed or the repo is corrupted, this failure goes completely unnoticed.
  Should at minimum log a warning to stderr.

[MED] llm.py:~278 — Hardcoded context window budget.
  `budget = 64000` is hardcoded. Different models have different context windows
  (DeepSeek V3 has 128k). This should either be configurable or derived from
  `config.model` metadata.

[MED] llm.py:~160–164 — Turn history cap uses `sorted(keys)[0]` (O(n log n)).
  For 200 entries this is fine, but a simpler approach (tracking `_min_turn` with an
  incrementing counter) would be O(1). Minor performance issue under heavy use.

[MED] llm.py:~256–257 — `turn_count == 0` check is outside the loop but `turn_count`
  was just set to 0 on the line above. This works correctly but is fragile — if this
  block is ever moved inside the loop (where `turn_count` gets incremented), it will
  never trigger. Consider using a dedicated boolean flag like `_git_diff_injected`.

[MED] llm.py:~480 — In the non-piping parallel tool execution path,
  `_append_tool_result` is called without `lock=tool_keys_lock`, but later in the
  piping path at line ~560 and ~630, the lock IS passed. Inconsistency: the
  non-piping path at line ~480 reads `recent_tool_keys` and calls `_append_tool_result`
  without passing `tool_keys_lock`, meaning the circuit breaker tracking is not
  properly synchronized in the non-piping parallel case.

[LOW] llm.py:~162 — `_save_turn_summary` truncates tool results to 150 chars but
  doesn't add an ellipsis indicator when truncated, unlike `_append_tool_result`
  which adds `…`. Minor inconsistency.

[LOW] llm.py:~54–78 — `call_deepseek` constructs `clean_messages` by stripping
  underscore-prefixed keys. If the message dict has a non-standard key that's
  underscore-prefixed but needed by the API (unlikely but possible), it gets
  stripped silently.

agent_runtime.py
======================================================================

[MED] agent_runtime.py:~199 — `get_inbox` returns a shallow copy of the list via
  `list(self.inboxes.get(task_id, []))`. This is thread-safe but allocates a new
  list on every call. If inboxes grow large, this becomes expensive. Consider
  returning a snapshot only when the caller actually needs isolation.

[MED] agent_runtime.py:~208 — `append_inbox` uses `dict.setdefault()` correctly,
  but there's no guard against unbounded inbox growth. If a sub-agent never reads
  its inbox, messages accumulate forever. Consider a cap per inbox.

[LOW] agent_runtime.py:~193–208 — Inbox and subscription management methods
  (`set_subscriptions`, `append_inbox`, `clear_inbox`) each acquire the lock
  independently. If called in rapid succession by the same caller, this could
  lead to subtle interleaving between lock acquisitions. Not currently a problem
  since these are called from single-threaded tool execution.

[LOW] agent_runtime.py:~218–223 — `active_count` property iterates all tasks
  under lock. For a small number of tasks this is fine, but if the registry grows
  large (e.g., 100+ concurrent sub-agents), the O(n) scan could become a bottleneck.

mini_agent.py
======================================================================

[MED] mini_agent.py:~110, ~125 — `_stats_lock` is defined twice. Line 110 creates
  a lock that is never used; line 125 overwrites it. The first lock is a dead
  object — remove it to avoid confusion.

[MED] mini_agent.py:~166–174 — In synchronous mode, `_tool_start_sync` modifies
  `stats["tool_calls"]` without holding `_stats_lock`. This is safe because
  synchronous mode has no concurrency, but it's inconsistent with the threaded
  path and would break if synchronous mode ever gained threading.

[MED] mini_agent.py:~220 — `session.close()` in the synchronous finally block has
  no error handling. If the session close raises (unlikely but possible with
  requests), the exception propagates unhandled. Wrap in try/except.

[LOW] mini_agent.py:~47–48 — `_approve` imports `from terminal import c, _YELLOW, _RED`
  at function scope. This is a deferred import inside a function that gets called
  per-tool-execution. Not a performance issue, but inconsistent with module-level
  imports elsewhere.

[LOW] mini_agent.py:~300–310 — Threaded mode quit/clear handlers set `_agent_cancel`
  then join with timeout=5. If the agent thread is stuck in a blocking
  subprocess/network call that doesn't check the cancel event promptly, the
  main thread hangs for 5 seconds. Consider making the timeout configurable or
  adding a "force quit" option.

stream.py
======================================================================

[HIGH] stream.py:~116–120 — Brace-balance pre-check for tool-call JSON completion
  can produce false negatives. The check `args.count("{") == args.count("}")` 
  assumes braces only appear as JSON delimiters. If a tool argument value contains
  a literal `{` or `}` (e.g., a code snippet, JSON string value, or regex pattern),
  the brace balance will be permanently wrong, and `on_tool_ready` will NEVER fire
  for that tool call, even after the stream completes. This means the tool call
  would go to the non-streaming execution path instead, losing the early-execution
  benefit. At minimum, the stream-end code should force-flush any unfired
  completed tool calls.

[MED] stream.py:~125 — Generic `except Exception: continue` silently swallows ALL
  exceptions during stream chunk processing, including KeyboardInterrupt and
  MemoryError. This should catch only `json.JSONDecodeError`, `KeyError`, and
  `ValueError` — the specific errors expected during JSON parsing of stream chunks.

[MED] stream.py:~55 — `response.iter_lines(decode_unicode=True)` buffers into memory.
  For very long streams (large file content in a single SSE message), the response
  body could be fully buffered. While SSE chunks are typically small, this is a
  potential memory issue with non-standard server implementations.

[LOW] stream.py:~127–131 — Connection-drop exception handling catches broad
  exception types (`requests.exceptions.ChunkedEncodingError`, `ConnectionError`,
  etc.) but doesn't distinguish between partial success (some tool calls completed)
  and total failure (nothing received). The caller might want to know the
  difference.

[LOW] stream.py:~75 — `if "usage" in chunk and chunk["usage"]:` — the truthiness
  check `chunk["usage"]` would fail if usage is an empty dict `{}`. While unlikely
  from the API, this double-check is unnecessary; `if "usage" in chunk` suffices
  since the API either omits it or includes a populated dict.

retry.py
======================================================================

[MED] retry.py:~47 — Hardcoded timeout tuple `timeout=(10, 120)`.
  The read timeout of 120 seconds is not configurable by the caller. Long-running
  streaming responses could timeout after 2 minutes. Consider making timeouts
  configurable via parameters.

[MED] retry.py:~32 — `_jittered_delay` uses `random.random()` without seeding.
  This is fine in production but makes retry timing non-deterministic in tests.
  Consider accepting an optional seed or using a `random.Random` instance for
  test reproducibility.

[LOW] retry.py:~60 — After exhausting all retries, the function returns the last
  response `r` instead of raising. This means the caller gets a non-OK response
  and must check `r.ok` themselves. While documented, this is inconsistent with
  the exception path (line 69: `raise last_exc` on network errors). Both paths
  should be consistent — either always raise or always return.

[LOW] retry.py:~40 — `kwargs.pop("stream", None)` removes `stream` from kwargs
  to avoid duplicates, but if the caller passes both `stream` as a positional
  arg in `*args` AND in `**kwargs`, it won't be caught. Highly unlikely but
  fragile.

--------------------------------------------------------------------------------
[HIGH] tools/__init__.py — _repair_json: unquoted key regex mutates also inside strings
--------------------------------------------------------------------------------
Lines 133–160, the fix3 regex `re.sub(r'(\w+)(\s*:)', r'"\1"\2', raw)` will match
bare words followed by colons inside string values (e.g. a JSON value like
`"foo: bar"` passed as an argument string). This can damage valid data during
repair attempts. The regex should skip content inside double-quoted strings.

--------------------------------------------------------------------------------
[HIGH] tools/__init__.py — _TOOL_CACHE uses sorted-args JSON; mutable args silently change key
--------------------------------------------------------------------------------
Line ~228: `cache_key = json.dumps([name, args], sort_keys=True)`. The `args` dict
may have been mutated by `args.pop("_pipe", None)` on line ~253 before the cache
write. This means the cache key used on read (before pop) differs from the key
used on write (after pop). The pipe pop happens between cache check and cache
store, so tools with `_pipe` will never hit the cache but could still write
entries under a different key, wasting memory with duplicate entries.

--------------------------------------------------------------------------------
[HIGH] tools/shell_ops.py — _TASK_REGISTRY leaks Popen objects; no cleanup on completion
--------------------------------------------------------------------------------
Lines ~85–90 + throughout: Background tasks are registered in `_TASK_REGISTRY`
dict with a Popen object keyed by uuid. Completed tasks are never removed from
this dict. Over a long session with many background tasks, this grows
unboundedly, leaks file descriptors (pipes stay open), and zombie processes
accumulate. `task_status` reports "completed" but never removes the entry.

--------------------------------------------------------------------------------
[HIGH] tools/shell_ops.py — _stream_reader collects all output unboundedly in list
--------------------------------------------------------------------------------
Lines ~50–58: `_stream_reader` appends every line to a `list[str]`. For
long-running commands or commands producing gigabytes of output, this will
exhaust memory. There is no size cap, backpressure, or streaming truncation
until after the process exits. This also affects background tasks where the
daemon threads drain into anonymous lists that are never consumed.

--------------------------------------------------------------------------------
[HIGH] tools/agent_ops.py — _COLLECT_ANY_POLL defined but never used; polling is lock-based
--------------------------------------------------------------------------------
Line ~390: `_COLLECT_ANY_POLL = 0.2` is defined but the `collect_any`
implementation delegates to `runtime._condition.wait_for()` instead. In the
meantime, the `fan_in()` function in `agent_patterns.py` does manual polling at
0.5s intervals via `runtime._condition.wait(timeout=0.5)` — using a different
polling interval. This inconsistency suggests dead code and a confused design.

--------------------------------------------------------------------------------
[HIGH] tools/mcp_client.py — _send_request blocks forever on concurrent responses
--------------------------------------------------------------------------------
Lines ~175–210: The `_send_request` method waits for a response with a matching
`id` in a `while True` loop. If the server sends responses for different
concurrent requests (e.g., from a prior reconnect), those responses are
silently discarded but the loop continues. If a concurrent call's response
is delayed and arrives out-of-order, the reading thread may consume and
discard it, causing the other caller to hang forever. The single stdout
reader + per-request queues pattern is missing.

--------------------------------------------------------------------------------
[HIGH] tools/mcp_client.py — disconnect may deadlock if Popen.wait() hangs
--------------------------------------------------------------------------------
Lines ~120–140: `disconnect()` calls `proc.stdout.readline()` indirectly via
the send_request loop (if a request is in-flight) while also calling
`proc.wait(timeout=3)`. There's no explicit thread-safety between disconnect and
in-flight `_send_request` calls. The lock serializes stdin writes but not
the stdout read loop. Two threads could deadlock: one in `_send_request`
reading stdout, another in `disconnect` waiting on `proc.wait`.

--------------------------------------------------------------------------------
[MED] tools/__init__.py — execute_tool signature mismatch: on_output not in tool schema
--------------------------------------------------------------------------------
Lines ~240–245: `execute_tool` takes `on_output: callable = None` but the
underlying tool implementations (e.g., `_run_shell`) expect `on_output` as
an additional argument. The dispatch logic at ~line 310 uses
`inspect.signature` to detect `on_output` in the function params. This is fragile:
if tool signatures are refactored, the inspection silently breaks and `on_output`
is never passed. Consider an explicit protocol or wrapper instead of runtime
introspection.

--------------------------------------------------------------------------------
[MED] tools/__init__.py — ToolResult.to_dict() mutates internal state (paranoia)
--------------------------------------------------------------------------------
Line ~40: `d: dict = {"success": self.success, "content": self.content}`. If a
caller modifies the returned dict, it doesn't affect ToolResult directly (safe
here), but there is no `__repr__` — debugging raw ToolResult objects in logs
is less informative than it could be.

--------------------------------------------------------------------------------
[MED] tools/file_ops.py — backup timestamp collisions possible under high concurrency
--------------------------------------------------------------------------------
Lines ~28–35: `_backup_before_write` uses `time.strftime("%Y%m%d_%H%M%S")` for
backup filename uniqueness. If two threads modify the same file within the same
second, the second backup overwrites the first, and only the last backup is
recoverable via `restore_file`. Use a higher-resolution timestamp or add a
random suffix.

--------------------------------------------------------------------------------
[MED] tools/file_ops.py — write_file re-indexes only .py files; edit_file does NOT
--------------------------------------------------------------------------------
Lines ~115–117: `write_file` calls `_reindex_file` for `.py` files.
`edit_file` (line ~145–199) never calls `_reindex_file`, so after an edit,
`find_symbol` and `find_usages` may return stale data. This is an asymmetry
that leads to stale symbol indices after edits.

--------------------------------------------------------------------------------
[MED] tools/file_ops.py — write_scratchpad bypasses safety gates for fallback path
--------------------------------------------------------------------------------
Lines ~330–345: When `scratchpad_path` is not set, `write_scratchpad` falls
back to writing `_TOOL_CONTEXT.workspace / ".mini_agent_scratchpad.md"` directly
without going through the write safety gate. This is a safety bypass.

--------------------------------------------------------------------------------
[MED] tools/file_ops.py — read_file offset applied after split, off-by-one confusion
--------------------------------------------------------------------------------
Lines ~72–78: `offset` is documented as "0-indexed line number." But the code
splits content by `splitlines(keepends=False)`, applies offset, then joins with
"\n". If the file uses `\r\n` line endings, the offsets will be correct (splitlines
handles this), but if the file has empty trailing lines, the `len(lines)` > actual
content lines — which is fine but may confuse users who count lines in their editor.

--------------------------------------------------------------------------------
[MED] tools/shell_ops.py — _check_destructive regex suffers from false positives
--------------------------------------------------------------------------------
Lines ~72–81: The pattern `r'\brm\b'` will flag commands containing "rm" as a
whole word, which can catch harmless commands mentioning "rm" in arguments
(e.g., `echo "confirm"` in scripts that chain operations). Also lacks patterns
for `shutdown`, `reboot`, `kill`, `pkill`, `:(){ :|:& };:` fork bomb variant.
The negative-lookahead approach is brittle.

--------------------------------------------------------------------------------
[MED] tools/shell_ops.py — run_shell background threads leak; no ownership tracking
--------------------------------------------------------------------------------
Lines ~115–125: Daemon threads started for stdout/stderr draining are never
tracked or cleaned up. If the parent process is long-lived, these threads
accumulate. Also, the threads read into anonymous lists `[]` that are GC'd
immediately if nobody references them — but the threads themselves persist
until the Popen process exits, potentially forever for hung processes.

--------------------------------------------------------------------------------
[MED] tools/search_ops.py — _semantic MaxEntries LRU: file ordering incorrect
--------------------------------------------------------------------------------
Lines ~230–235: When a file is re-indexed, it's appended to `_SEMANTIC_LRU`.
But `_SEMANTIC_LRU` tracks access order for eviction, not insertion order.
If a file is only indexed once but searched many times, it should NOT be at
risk of eviction. The LRU should be touched on access (semantic_search),
not just on insertion.

--------------------------------------------------------------------------------
[MED] tools/search_ops.py — build_symbol_index walks files even when cache is fresh
--------------------------------------------------------------------------------
Lines ~90–100: The "check mtime while walking" pattern walks all directories
and checks file mtimes even when `needs_rebuild` is False, just to confirm
freshness. This means every `find_symbol` call that triggers index loading
does a full os.walk() even when the on-disk cache is perfectly fresh. The
walk is cheap but unnecessary — checking the cache file's mtime against a
global "last seen max mtime" would be faster.

--------------------------------------------------------------------------------
[MED] tools/search_ops.py — semantic_search imports numpy inside function repeatedly
--------------------------------------------------------------------------------
Lines ~302: `import numpy as np` is inside `_semantic_search`. For a
cached/lazy import this is fine, but `_sem_index` (called by the same tool)
also uses numpy without importing it — relying on the implicit import from
the call stack. This is fragile. Also, the `np.asarray(embs)` call on a list
of individual numpy arrays creates a ragged-array risk if embeddings ever
have different shapes.

--------------------------------------------------------------------------------
[MED] tools/agent_ops.py — spawn_agent batch mode silently caps at _MAX_CONCURRENT
--------------------------------------------------------------------------------
Lines ~145–155: The batch-spawn loop breaks when `runtime.active_count >=
_MAX_CONCURRENT`. It doesn't report how many were skipped, so the caller
may think all tasks were spawned. The return says "Spawned N sub-agent(s)"
but N may be less than the input list length with no warning.

--------------------------------------------------------------------------------
[MED] tools/agent_ops.py — agent_extend not fully read; likely missing max_turns clamp
--------------------------------------------------------------------------------
The visible code doesn't show the actual turn-extension logic (file truncated
at line 934), but based on the pattern, agent_extend should enforce a cap to
avoid infinite extension. If missing, a parent could extend a sub-agent
indefinitely.

--------------------------------------------------------------------------------
[MED] tools/agent_messages.py — _validate_payload accepts unknown keys silently
--------------------------------------------------------------------------------
Lines 142–155: The validation loop iterates over `payload.items()`. For keys
NOT in the schema, it raises ValueError. For keys IN the schema, it checks
types. But if the schema has a key with an unknown type string (not in
_TYPE_CHECKERS), it `continue`s — allowing any value through. This is
documented as "unknown type string — allow it" but means typos in type
registration (e.g., `"str"` instead of `"string"`) silently accept any value.

--------------------------------------------------------------------------------
[MED] tools/agent_messages.py — _route_message uses setdefault on every delivery
--------------------------------------------------------------------------------
Lines 200–207: `inboxes.setdefault(task_id, [])` is called for every
message delivery, even though the inbox for each task_id should already
exist. Minor allocation overhead, but repeated calls in a tight loop with
many messages creates many temporary empty-lists that are immediately
discarded if the key exists.

--------------------------------------------------------------------------------
[MED] tools/agent_patterns.py — fan_in timeout doesn't cancel unfinished tasks
--------------------------------------------------------------------------------
Lines 85–120: When `fan_in` times out, it returns `None` for pending tasks
but does NOT cancel them. The sub-agents continue running in the background,
consuming resources with no collector. The caller receives no indication that
tasks are still running. Consider adding explicit cancellation or at least
noting pending tasks in the return value.

--------------------------------------------------------------------------------
[MED] tools/agent_patterns.py — pipeline doesn't handle stage failure cleanup
--------------------------------------------------------------------------------
Lines 130–175: If a middle stage fails (`prev_result` is None or not
`prev_result.success`), the pipeline returns immediately without cancelling
already-spawned subsequent stages (they haven't been spawned yet in the
sequential design, so this is actually fine). But earlier stages that
completed and spawned sub-agents for coordination are not cleaned up.

--------------------------------------------------------------------------------
[MED] tools/mcp_client.py — tool schemas from MCP servers mutate TOOLS list globally
--------------------------------------------------------------------------------
Lines ~440–460: `_register_server_tools` does `TOOLS.append(...)` directly
on the imported list from `tools.schema`. This is a global mutable append.
If the manager is re-initialized (e.g., after a reconnect loop), tools are
re-registered and the list grows unboundedly with duplicates. There's no
cleanup of old registrations before re-registration.

--------------------------------------------------------------------------------
[MED] tools/mcp_client.py — reconnect after BrokenPipeError: 2nd send_request may hang
--------------------------------------------------------------------------------
Lines ~280–295: `call_tool` catches connection errors, calls `self.reconnect()`,
and retries the request. But `reconnect()` calls `disconnect()` which closes
stdin and waits for the process. While this is happening, the old `_send_request`
may still be blocked reading stdout from the dead process. The lock serializes
stdin writes but there's a TOCTOU window: a thread could be between the lock
release in `disconnect` and the lock acquire in `_start_process`.

--------------------------------------------------------------------------------
[LOW] tools/__init__.py — set_context silently ignores unknown keys via setattr
--------------------------------------------------------------------------------
Lines ~107–112: `set_context` handles known keys explicitly but falls through
to `setattr(ctx, key, value)` for unknown keys. This means typos in key names
(e.g., `workspce` instead of `workspace`) silently create dead attributes on
the context object instead of raising an error.

--------------------------------------------------------------------------------
[LOW] tools/__init__.py — CACHEABLE set doesn't include find_symbol, find_usages
--------------------------------------------------------------------------------
Line ~100: `find_symbol` and `find_usages` are read-only tools that could
benefit from caching within a turn, but they're not in `_CACHEABLE`. Their
results can be large but caching would avoid redundant symbol lookups when
the agent calls `find_symbol` for the same symbol twice in one turn.

--------------------------------------------------------------------------------
[LOW] tools/schema.py — TOOLS is mutable global; no deep-copy protection
--------------------------------------------------------------------------------
The TOOLS list is defined at module level and imported by other modules
that mutate it (e.g., mcp_client.py). There's no mechanism to reset TOOLS
to its original state. If tests need to clear MCP-registered tools, they
must manually splice the list.

--------------------------------------------------------------------------------
[LOW] tools/file_ops.py — edit_file candidate search uses incomplete substring match
--------------------------------------------------------------------------------
Lines ~175–180: The old_string-not-found hint searches for lines containing
`old_first_line[:30]`. If `old_string` has no newlines, `old_first_line` is
the whole string, and the 30-char truncation can produce false matches on
unrelated lines that happen to share a 30-char prefix. This is minor (hint
only) but could confuse the agent.

--------------------------------------------------------------------------------
[LOW] tools/file_ops.py — _BACKUPS dict never cleaned; grows with every write
--------------------------------------------------------------------------------
The `_BACKUPS` dict maps resolved paths to backup paths. `restore_file`
removes entries. But if the agent writes 1000 different files in a session
without restoring, the dict retains all 1000 entries. Each entry is small
(a few strings), so memory impact is low, but it's still a slow leak.

--------------------------------------------------------------------------------
[LOW] tools/shell_ops.py — duped lint step in verify: step 1 runs pytest test_lint,
then step 3 runs flake8 separately
--------------------------------------------------------------------------------
Lines ~360–370 and ~380–395: verify() runs `pytest test_lint.py` first, then
later runs `flake8` as a separate "lint job". The function comment says "Step 1:
lint" and then does it again as a parallel job. The first lint is serial and
unnecessary if the second is parallel. This is redundant and slows down verify.

--------------------------------------------------------------------------------
[LOW] tools/shell_ops.py — git restore subcommand calls git diff first then restore
--------------------------------------------------------------------------------
Lines ~695–710: The `restore` subcommand runs `git diff --name-only HEAD` and
then `git restore`. The diff result is used only for the success message,
not for decision-making. If diff fails, the restore still proceeds but the
error from diff masks the restore result. Also, the restore paths split from
`extra` do not handle files with spaces in names.

--------------------------------------------------------------------------------
[LOW] tools/search_ops.py — symbol_index disk cache lacks corruption handling
--------------------------------------------------------------------------------
Lines ~60–70: The `build_symbol_index` function tries to read the disk cache
JSON. If the JSON is truncated or corrupted mid-write (e.g., process crash
during prior atomic rename), `json.loads` will fail silently via the bare
except, and the index is rebuilt. This is correct behavior but there's no
log message when this happens, making debugging hard.

--------------------------------------------------------------------------------
[LOW] tools/search_ops.py — _reindex_file has a race: index rebuilt during reindex
--------------------------------------------------------------------------------
Lines ~175–240: `_reindex_file` checks `if _SYMBOL_INDEX is None: return`.
If another thread triggers `build_symbol_index` between this check and the
subsequent mutations, the reindexed entries are overwritten by the full
rebuild. Since Python has GIL, this isn't a data-corruption race but the
reindex work is silently lost.

--------------------------------------------------------------------------------
[LOW] tools/agent_ops.py — _AGENT_MSGS flat list grows forever
--------------------------------------------------------------------------------
Lines ~35: `_AGENT_MSGS` is a module-level list that only grows. Messages are
never pruned. In a long session with many sub-agents broadcasting, this list
could consume significant memory. `agent_read` with `since` index avoids
re-reading old messages but doesn't enable cleanup.

--------------------------------------------------------------------------------
[LOW] tools/agent_patterns.py — fan_out doesn't respect subscriptions parameter
--------------------------------------------------------------------------------
Lines ~60–75: `fan_out` accepts a `subscriptions` parameter and passes it to
`_spawn_one` via a check after spawning (`if subscriptions:`), but `_spawn_one`
also accepts a `subscriptions` parameter that's only used in the `spawn_agent`
tool, not in the `_spawn_one` signature as defined in `agent_ops.py`. Wait —
looking more carefully, `_spawn_one` in `agent_ops.py` line ~70 does accept
`subscriptions` and calls `runtime.set_subscriptions`. But in `fan_out`, the
call to `_spawn_one` at line ~66 does NOT pass `subscriptions=subscriptions`.
It instead sets them after the fact. This means there's a window where
messages could be missed if they arrive between spawn and set_subscriptions.

--------------------------------------------------------------------------------
[LOW] tools/mcp_client.py — MCP process stderr is not drained
--------------------------------------------------------------------------------
Lines ~140–155: `_start_process` creates the subprocess with `stderr=PIPE`
but the stderr pipe is never read. If the MCP server writes diagnostic output
to stderr, the pipe buffer fills up (typically 64KB on Linux) and the server
blocks on write, effectively deadlocking the connection. A daemon thread
should drain stderr.

--- memory.py ---

[ 1] [HIGH]   memory.py:341 — Redundant `self._ensure_table()` call.
        __init__ already creates the table in lines 318-340 (via sqlite3.connect,
        execute CREATE TABLE, commit, close). Then line 341 calls _ensure_table()
        which opens a second connection and re-runs CREATE TABLE. This wastes an
        extra connection and I/O on every MemoryStore construction. Remove the
        redundant call or move the table creation into _ensure_table exclusively.

[ 2] [HIGH]   memory.py:406-407 — `_last_saved_count` updated even on save failure.
        self._last_saved_count = len(kept) is outside the try/except block
        (line 407). If the SQLite write fails (e.g. disk full, locked DB),
        _last_saved_count still advances. On the next save(), the incremental
        append path (new_msgs = kept[self._last_saved_count:]) will skip messages,
        causing silent data loss. Move the assignment inside the try block, after
        the commit succeeds.

[ 3] [MED]    memory.py:392 — Incremental save uses `BEGIN IMMEDIATE` but has no
        explicit ROLLBACK on exception. If conn.executemany raises mid-INSERT,
        the transaction stays open until the connection context manager cleans up.
        Python's sqlite3 library will implicitly rollback on __exit__ if an
        exception is caught, but relying on this is fragile — an explicit
        conn.rollback() in an except block would be clearer and safer.

[ 4] [MED]    memory.py:370-381 — save() does compression, pruning, and summary
        injection *before* opening the DB transaction. If any of these in-memory
        operations modify `kept` but the DB write fails, there's no way to recover
        the original state. Consider computing the final `kept` list, then
        writing atomically.

[ 5] [MED]    memory.py:410-420 — `clear()` catches sqlite3.Error and falls back
        to `os.remove(db_path)`, but `os.remove` can fail with PermissionError
        or OSError on Windows (file locked by another process). Only
        FileNotFoundError is caught. A bare `except OSError` would be safer.

[ 6] [LOW]    memory.py:89-120 — `_compress_tool_results`: the `keep_recent` 
        parameter defaults to 6, but the docstring says "more than N messages 
        ago." The cutoff = len(messages) - keep_recent means only the last 6 
        messages are preserved — this includes user and assistant messages,
        not just tool results. This is misleading: non-tool messages in the
        tail count against the "recent" budget. Consider clarifying that
        `keep_recent` counts all message types, not just tool results.

[ 7] [LOW]    memory.py:55-68 — `_estimate_tokens` for assistant messages with
        tool_calls: adds len(content) + len(json.dumps(arguments)) but this 
        double-counts the tool_call function name and id fields, omitting them
        from the estimate. While these are small, a more accurate estimate would
        include the full tool_calls JSON blob: len(json.dumps(msg["tool_calls"])).

[ 8] [LOW]    memory.py:619 — `_migrate_json` reads the entire JSON file into
        memory with `json.load(f)`. For very large JSON files (e.g. multi-MB
        legacy memory), this could cause OOM or long pauses. Streaming reads
        aren't straightforward with json.load, but a size check before loading
        would at least prevent OOM crashes.

[ 9] [LOW]    memory.py:425-467 — `get_scratchpad`, `set_scratchpad`, 
        `get_test_output`, `save_test_output` all open separate connections

[10] [LOW]    memory.py:340 — `_ensure_table` silently catches sqlite3.Error.

--- safety.py ---

[11] [HIGH]   safety.py:80-83, 150-152 — TOCTOU race between realpath() and
        open()/write(). The comments acknowledge this, but the implication is
        that a symlink swap between the path resolution and the actual file
        operation could allow writes outside the workspace. While the window is
        small, the risk is real for a programmatic agent that operates at API
        speed. Consider using `open(..., dir_fd=...)` with directory file
        descriptors to close the window (Linux-specific, but worth the platform
        check).

[12] [MED]    safety.py:49,107 — No validation that `workspace_root` exists or
        is a directory. If a user passes a non-existent path (e.g. "--workspace

        abspath still produces an absolute path for non-existent files). The
        resolved root may be completely wrong, and all subsequent boundary
        checks become meaningless. Add `os.path.isdir(self._root)` validation
        in __init__.

[13] [MED]    safety.py:19-22 — `_is_within_workspace` check `resolved.startswith
        (root + os.sep)` is correct for preventing `/workspace-other` bypasses.
        However, the fallback `or resolved == root` only matches exactly the
        root path. If root is `/home/user/project` and resolved is
        `/home/user/projectfile` (no separator), this is correctly blocked by
        the startswith check. No bug here, but consider using
        `os.path.commonpath([resolved, root]) == root` as a more robust check
        that also handles edge cases with trailing slashes.

[14] [LOW]    safety.py:150 — `os.path.isfile(resolved)` is itself a TOCTOU

        The overwrite guard is best-effort; using O_EXCL in the actual file

[15] [LOW]    safety.py:36-38 — `ReadSafetyResult` and `WriteSafetyResult` are

1. [HIGH] DEADLOCK — Lock inversion between _lock and _condition
   agent_runtime.py:88-100 (store_result), agent_runtime.py:109-112 (get_status)
   tools/agent_ops.py:345-346 (collect_agent)
   
   store_result() acquires self._lock FIRST, then enters with self._condition.
   collect_agent() calls _condition.wait_for(_completed, ...) which acquires
   the condition's internal lock, then the predicate _completed() calls
   get_status() which acquires self._lock. This is an inverted lock ordering:
   
     Path A (collect_agent): condition lock → _lock (inside predicate)
     Path B (store_result):  _lock → condition lock
   
   If thread A holds the condition lock (inside wait_for's predicate) and
   blocks waiting for _lock, while thread B holds _lock and blocks waiting
   for the condition lock, both threads deadlock.
   
   FIX: Never hold the condition lock while acquiring _lock in the predicate.
   Use a separate event or restructure so store_result() notifies the condition
   WITHOUT holding _lock, or have the predicate check state without acquiring
   _lock (e.g., use an atomic flag).

2. [HIGH] Lost-wakeup race in fan_in() and pipeline()
   tools/agent_patterns.py:110-117 (fan_in), tools/agent_patterns.py:160-175 (pipeline)
   
   Both functions call runtime.get_status(tid) OUTSIDE the condition lock,
   then call runtime._condition.wait(timeout=...). Between get_status()
   returning "running" and _condition.wait() acquiring its internal lock,
   store_result() can fire and call _condition.notify_all(). That notify
   is delivered to NO ONE because the waiting thread hasn't entered wait()
   yet. The result: the collector sleeps for the full timeout (0.5s per
   iteration) even though the result is ready.
   
   Contrast with collect_agent (agent_ops.py:345) which correctly uses
   _condition.wait_for(predicate, timeout=...) — this atomically checks
   the predicate under the condition lock, eliminating the TOCTOU gap.
   
   FIX: Use wait_for() with a predicate, or do the status check inside
   a with runtime._condition: block.

3. [HIGH] handoff.result and handoff.request produce garbled 'task' field
   tools/agent_ops.py:670-674 (_agent_handoff)
   
   For handoff.result:
       payload = {"result": result_payload, "task": str(result_payload)}
   For handoff.request:
       payload = {"task": str(result_payload), "input_schema": result_payload}
   
   result_payload is a dict (e.g. {"count": 42, "task": "count items"}).
   str(result_payload) produces Python dict repr like "{'count': 42, 'task': 'count items'}".
   This passes schema validation (it's a string) but the 'task' field is
   semantically garbage — not a human-readable task description.
   
   The caller already passes a 'task' key inside result_payload in many cases
   (see test_agent_messages.py: "result": {"count": 42, "task": "count items"}),
   but the code never extracts it. It stringifies the entire dict instead.
   
   FIX: Extract task description from result_payload.get("task", "") or
   require the caller to pass a separate 'task' parameter.

4. [HIGH] Memory leak — inboxes and subscriptions never cleaned up
   agent_runtime.py:88-100 (store_result)
   
   store_result() removes task from self.tasks, self.cancel_events, and
   self.max_turns, but does NOT clean up self.inboxes or self.subscriptions.
   A clear_inbox() method exists (agent_runtime.py:179-183) but is never
   called. Every completed sub-agent leaks its inbox messages and subscription
   metadata forever.
   
   FIX: Call self.clear_inbox(task_id) inside store_result() after storing
   the result. Or add it to the cleanup block.

5. [MEDIUM] collect_any uses static candidate list — misses agents spawned after
   tools/agent_ops.py:425-430 (_collect_any)
   
   When task_ids is not provided, candidates is built once as the union of
   runtime.tasks and runtime.results at that moment. New agents spawned after
   this point are invisible to the predicate _any_completed(). If all current
   agents are slow but a fast agent is spawned later, collect_any won't notice
   the fast one completes.
   
   FIX: Rebuild candidates inside the predicate, or use the global task list
   in the predicate closure.

6. [MEDIUM] fan_out sets subscriptions AFTER thread start — missed-message window
   tools/agent_patterns.py:54-84 (fan_out)
   
   fan_out() calls _spawn_one() which starts the sub-agent thread, THEN calls
   runtime.set_subscriptions(tid, subscriptions). There is a narrow window
   between thread start and set_subscriptions where messages routed to this
   agent could be missed if the agent's subscriptions would have caught them.
   
   _spawn_one() itself accepts a 'subscriptions' parameter and passes it to
   _spawn_agent, which calls runtime.set_subscriptions() BEFORE thread.start()
   (agent_ops.py:126). But fan_out doesn't pass 'subscriptions' to _spawn_one.
   
   FIX: Pass subscriptions=subscriptions to _spawn_one() in fan_out().

7. [MEDIUM] scatter_gather has no subscriptions parameter
   tools/agent_patterns.py:238-276 (scatter_gather)
   
   scatter_gather() builds worker descriptions and calls fan_out(), but
   does not accept or forward a 'subscriptions' parameter. Workers spawned
   via scatter_gather can never have custom subscriptions. This limits the
   pattern's usefulness with typed message routing.
   
   FIX: Add a 'subscriptions' parameter and forward it to fan_out().

8. [MEDIUM] Batch spawn silently truncates when at capacity — caller not informed
   tools/agent_ops.py:110-115 (_spawn_agent batch path)
   
   The for-loop over valid_tasks breaks when runtime.active_count >= _MAX_CONCURRENT.
   If 5 tasks are requested but only 3 slots are free, 3 spawn successfully
   and the tool returns success. The caller has no way to know 2 tasks were
   dropped. The only failure case is when ALL tasks are dropped.
   
   FIX: Return the count of dropped tasks in the result content, or use a
   partial-success indicator.

9. [MEDIUM] SubAgentResult.to_json() drops scratchpad and error fields
   agent_runtime.py:46-55 (to_json)
   
   to_dict() returns 6 fields (success, content, turns_used, tool_calls_made,
   scratchpad, error). to_json() only serializes 4 fields, omitting scratchpad
   and error. This inconsistency means error information and final scratchpad
   state are lost when the result is serialized via to_json().
   
   FIX: Include all fields in to_json(), or add a docstring explaining the
   intentional omission.

10. [MEDIUM] _AGENT_MSGS global list grows unbounded — no pruning
    tools/agent_ops.py:40 (_AGENT_MSGS)
    
    The legacy flat message list (_AGENT_MSGS) has no size cap, no pruning,
    and no cleanup. Over a long session with many sub-agents broadcasting
    messages, this list can grow to consume significant memory. Every
    agent_read() call copies the entire list.
    
    FIX: Add a maximum size (e.g., 500 messages), evict oldest when exceeded.
    Or prune on agent_read() with a sliding window.

11. [MEDIUM] _route_message holds _lock for entire routing loop — blocks runtime
    tools/agent_messages.py:193-222 (_route_message)
    
    _route_message() acquires the shared runtime._lock and iterates over all
    subscriptions, appending to inboxes. With many subscribed agents, this
    holds the runtime's primary lock for the duration. During this time, all
    task status queries, spawns, cancellations, and result stores are blocked.
    
    FIX: Use a separate lock for inboxes/subscriptions, or snapshot the
    subscription list under lock, then deliver messages outside the lock.

12. [MEDIUM] Two separate messaging systems: _AGENT_MSGS (legacy) vs inboxes
    tools/agent_ops.py:40-42 (_AGENT_MSGS, _AGENT_MSGS_LOCK)
    
    agent_message and agent_handoff write to BOTH _AGENT_MSGS and runtime.inboxes.
    agent_read reads from _AGENT_MSGS only. agent_inbox reads from runtime.inboxes
    only. A sub-agent using agent_read sees all messages unfiltered; a sub-agent
    using agent_inbox sees only subscription-filtered messages. There is no
    single source of truth, and no way to drain both simultaneously.
    
    FIX: Deprecate one path, or make agent_read a wrapper over the inbox system.

13. [MEDIUM] barrier() uses polling-only — no event-driven notification
    tools/agent_patterns.py:178-215 (barrier)
    
    barrier() checks each agent's inbox for coord.sync messages, then sleeps
    0.2 seconds in a polling loop. It never calls _condition.wait(). If no
    agent sends a coord.sync message, barrier() spins until timeout (120s).
    There's no proactive notification when a sync message arrives in an inbox.
    
    FIX: Add a threading.Event or use _condition.notify_all() when a coord.sync
    message is routed to an inbox, so barrier() can wake immediately.

14. [MEDIUM] _route_message's 'routed' variable is dead code
    tools/agent_messages.py:216-222
    
    The 'routed' boolean is set to True when a message is delivered but never
    read, returned, or logged. It's purely dead code. If the intent was to
    warn when a message goes unrouted, that logic is missing.
    
    FIX: Either remove 'routed' or use it to log a warning when no agent
    received the message.

15. [LOW] config.stream race between concurrent visible/non-visible sub-agents
    tools/agent_ops.py:93-98 (_runner)
    
    Each sub-agent's _runner saves config.stream as original_stream, sets it
    to True if visible, then restores it in finally. If a visible and a
    non-visible sub-agent run concurrently, their save/restore of the shared

16. [LOW] Orphaned task if thread.start() raises
    tools/agent_ops.py:119-126 (_spawn_one)
    
    runtime.register() is called before thread.start(). If thread.start()
    raises (e.g., RuntimeError on an already-started thread), the task is
    registered as "running" but never actually executes. It will remain
    "running" forever, consuming a slot in the active count.
    
    FIX: Wrap thread.start() in try/except, and call runtime.cancel() or
    store_result() on failure to clean up.

17. [LOW] _validate_payload silently passes unknown type strings
    tools/agent_messages.py:162-164 (_validate_payload)
    
    When a schema specifies a type string not in _TYPE_CHECKERS, the checker
    lookup returns None and the function does "continue  # unknown type string
    — allow it". This means typos in type registrations (e.g., "strng" instead
    of "string") are silently ignored, defeating validation.
    
    FIX: At minimum, log a warning. Better: raise an error for unknown type
    strings during registration, not during validation.

18. [LOW] AgentMessage.timestamp uses time.monotonic which is not wall-clock
    tools/agent_messages.py:103
    
    time.monotonic is not comparable to wall-clock time. It's fine for
    ordering within a single process but can't be correlated with logs or
    external timestamps. For a messaging system, time.time() might be more
    useful for debugging.
    
    FIX: Consider using time.time() for human-readable timestamps, or document

19. [LOW] run_sub_agent re-reads max_turns only at turn boundaries
    sub_agent.py:87-93
    
    The sub-agent loop checks for updated max_turns only at the top of each
    while iteration. If agent_extend extends the budget mid-turn (during a
    tool call or LLM invocation), the sub-agent won't see the new budget
    until the next turn starts. This means the extension isn't immediately
    effective.
    
    FIX: Acceptable as-is (extensions are coarse-grained), but document the
    behavior or check max_turns more frequently.

20. [LOW] _SUB_AGENT_SYSTEM_PROMPT reference is module-level but defined at bottom
    sub_agent.py:66-69, sub_agent.py:234-262
    
    _SUB_AGENT_SYSTEM_PROMPT is referenced at line 67 inside run_sub_agent()

[HIGH] eval/runner.py:274 — MetricsCollector.turn_count is always 1.

  The function runs `git add -A` then `git commit -m "Initial state"`. If the
  workspace directory is empty (no files to commit), `git commit` will fail
  with "nothing to commit". This happens when workspace_fixture is None and
  no files are copied (e.g., if ignore patterns exclude everything).
  Fix: use `git commit --allow-empty` or check for files first.

[MED] eval/runner.py:223 — shutil.copytree copies .git from source workspace.
  When workspace_fixture is None, the code copies the entire current workspace
  via shutil.copytree. The _IGNORE_PATTERNS tuple excludes .git, but if the
  current workspace HAS a .git directory (copytree is called with
  ignore=shutil.ignore_patterns(*_IGNORE_PATTERNS)), .git is excluded correctly.
  However, _ensure_git_repo is called immediately after, which runs git init.
  If the source workspace had staged/uncommitted changes that the agent relies
  on, those are lost. This is by design but worth noting.

[MED] eval/scorer.py:128 — shell checker raises on failed shlex.split.
  shlex.split(params["command"]) is called without a try/except. If the command
  has unbalanced quotes, shlex.split raises ValueError, which becomes a
  generic "Checker error: ..." via run_checks. Should catch ValueError and
  return a CheckResult with detail "Invalid shell command syntax".

TEST DESIGN PROBLEMS
==============================================================================

[DESIGN] test_eval.py:525-600 — run_suite_manual duplicates run_suite logic.
  The test helper recreates the aggregation logic from run_suite inline. If
  run_suite changes (e.g., adds new metric fields), the test helper diverges
  silently. Tests should call the real run_suite() with mocked run_task
  instead of bypassing it.

[DESIGN] test_eval.py:34-100 — YAML parsing tests use inline strings.
  The inline YAML strings in TestTaskYAMLParsing use excessive backslash
  escaping (e.g., "range\\\\\\(1, n \\\\\\\\+ 1\\\\\\)") which is hard to
  read and verify. Better to use dedent or read from real YAML files in
  the tasks directory.

[DESIGN] test_eval.py — All runner tests mock the entire agent loop.
  No test runs the real agent loop against a trivial task. This means the
  runner → agent integration is never tested. A simple integration test
  (e.g., a task with shell checker that the agent can trivially pass) would
  catch regressions in the runner/agent interface.

[DESIGN] test_eval.py:185 — test_passes test requires pytest in environment.
  If pytest is not installed in the current Python environment, the
  TestCheckerTestPasses tests will fail with a misleading error (non-zero
  returncode from `python -m pytest`). Should add a pytest.mark.skipif
  that checks for pytest availability.

[DESIGN] test_eval.py:637 — _init_git helper duplicates _ensure_git_repo.
  The test file defines its own _init_git and _git_add_commit helpers that
  replicate git setup logic from runner._ensure_git_repo. If the runner's
  git setup changes (e.g., adds user.name config), the tests diverge.

METRICS CALCULATION ERRORS

[METRICS] eval/metrics.py + eval/runner.py — Tool names extracted from summary.
  MetricsCollector.on_tool_start extracts the tool name by splitting on '('.
  Line: name = summary.split("(", 1)[0].strip() if "(" in summary else summary
  This is fragile — if the summary format changes or doesn't include parens,
  the name extraction breaks silently. The tool dispatch system knows the
  exact tool name; consider adding a "tool_name" parameter to the callback.

[METRICS] eval/runner.py:297 — Token estimation is approximate.
  from memory import _total_tokens
  tokens = _total_tokens(session["messages"])
  _total_tokens (memory.py:75) estimates tokens as len(text)//4 with max(1,...).
  This is a rough heuristic (4 chars ≈ 1 token for English). The EvalResult
  says "tokens_consumed" but this is really an estimate. Document the
  approximation or use tiktoken for accurate counting.

[METRICS] eval/runner.py:388 — Suite pass_rate includes errors in denominator.
  Line: pass_rate=passed / total if total > 0 else 0.0
  where total = passed + failed + errors. So pass_rate = passed/(passed+failed+errors).
  This is intentional (total tasks) but differs from some conventions where
  pass_rate = passed/(passed+failed) excluding errors. Document the convention
  in the SuiteReport docstring.

[METRICS] eval/runner.py — Tool usage aggregation double-counts?
  In run_suite, tool_usage is aggregated per-task. Each run_task creates a new
  MetricsCollector and returns tool_calls as dict(metrics.tool_counts). The
  aggregation sums across tasks — this is correct. No double counting.
