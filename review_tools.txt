  2. Prefer explicit control flow over hidden magic
  3. No circular imports. No global mutable state unless unavoidable

  5. All tool results must be structured — never raw exceptions
  6. Every file write must go through the safety layer
  7. Every new feature needs at least one test
  8. Prefer small incremental edits over large rewrites
  9. Prefer readable code over clever code

 11. Keep prompts, execution logic, tools, and memory in separate modules
 12. Do not create new subsystems unless the existing architecture cannot handle the need
 13. Reuse existing abstractions before introducing new ones
 14. Avoid duplicate logic; extract shared behavior carefully

VIOLATION 1: Cache key mismatch — _pipe present during check, absent during store
================================================================================
File: tools/__init__.py, lines ~264-268 (check) vs lines ~327-329 (store)
Principle: 2 (explicit control flow), Principle: cache correctness

The cache check at line 264 computes `cache_key` using `args` BEFORE `_pipe` is
popped (line 272). The cache store at line 327 computes `cache_key` AFTER `_pipe`
is popped. This means any read-only call that includes a `_pipe` field will NEVER
hit the cache, because the check key differs from the stored key.

Example:
  First call with _pipe:    check key = [name, {path:..., _pipe:{...}}] → miss
                            pop _pipe
                            store key = [name, {path:...}]  (different!)
  Second call with _pipe:   check key = [name, {path:..., _pipe:{...}}] → miss again

Suggested fix: Move the _pipe pop BEFORE the cache check so both use the same key.

  # --- strip _pipe meta-field before anything else ---
  pipe_config = None
  if isinstance(args, dict):
      pipe_config = args.pop("_pipe", None)

  # THEN check cache
  if on_output is None and name in _CACHEABLE:
      cache_key = json.dumps([name, args], sort_keys=True)
      ...

VIOLATION 2: Write operations do not invalidate the read cache
================================================================================
File: tools/__init__.py, line 327; tools/file_ops.py lines ~117, ~200
Principle: 2 (explicit control flow), Principle: cache correctness

`write_file` and `edit_file` successfully modify a file on disk, but the
per-turn read cache (`_TOOL_CACHE`) is not invalidated for that file path.
If a read_file("foo.py") was cached earlier in the turn and then a
write_file("foo.py", ...) occurs, a subsequent read_file("foo.py") will
return the stale cached content — not the just-written content.

The cache is only cleared once per turn via `clear_tool_cache()` (line ~107)
at the start of each turn. Within a turn, writes can cause stale reads.

Suggested fix: In `_write_file` and `_edit_file`, after a successful write,
invalidate cache entries for the written path.

  from tools import _TOOL_CACHE, _CACHEABLE
  keys_to_del = [k for k in _TOOL_CACHE if resolved_path in k]
  for k in keys_to_del:
      del _TOOL_CACHE[k]

VIOLATION 3: restore_file discards raw path instead of resolved_path
================================================================================
File: tools/file_ops.py, line ~434-435
Principle: 2 (explicit control flow)

  _MODIFIED_FILES.add(safety_result.resolved_path)   # in write_file (line ~126)
  _MODIFIED_FILES.discard(path)                      # in restore_file (line ~434)

`_MODIFIED_FILES` stores resolved absolute paths (from safety_result.resolved_path),
but `restore_file` discards the raw user-supplied `path` (args["path"]).
If `path` is relative and the resolved path is absolute, the discard is a no-op
and the entry leaks in `_MODIFIED_FILES` forever.

Suggested fix: Use `resolved` instead of `path`:
  _MODIFIED_FILES.discard(resolved)

VIOLATION 11: _repair_json — unquoted-key regex matches inside string values
================================================================================
File: tools/__init__.py, lines ~152-154
Principle: 5 (structured results), Principle: 9 (correctness over cleverness)

The regex `r'(\w+)(\s*:)'` used to quote unquoted keys will also match inside
string values. For example, the JSON string `{"key": "abc: def"}` would be
corrupted to `{"key": "abc": def"}`. Similarly, the single-quote-to-double-quote
replacement (`raw.replace("'", '"')`) breaks any legitimate single quotes inside
string values.

These repair heuristics are applied blindly without awareness of whether the
match occurs inside a string literal.

Suggested fix: At minimum, add a comment acknowledging the limitation. A more
robust fix would tokenize the raw string first to skip quoted contexts, but
that may be over-engineering. Consider using `json5` or `demjson3` instead of
custom repair.

VIOLATION 14: Duplicate safety-gate failure pattern in every tool
================================================================================
Files: file_ops.py, shell_ops.py, search_ops.py — every tool implementation
Principle: 14 (avoid duplicate logic), Principle: 13 (reuse existing abstractions)

Nearly every tool repeats the same 4-line pattern:

  safety_result = rg.check(path)
  if not safety_result.allowed:
      return ToolResult(
          success=False,
          content=f"<Tool> blocked by safety layer: {safety_result.reason}",
      )

This appears in read_file, write_file, edit_file, list_directory, file_info,
search_files, semantic_search, restore_file, and more. Write-gate checks
duplicate it with wg.check().

Suggested fix: Extract a decorator or helper:
  def _require_read_access(rg, path, tool_name):
      result = rg.check(path)
      if not result.allowed:
          return ToolResult(False, f"{tool_name} blocked: {result.reason}")
      return result  # caller checks for ToolResult vs SafetyResult

Or use a context-manager pattern.

VIOLATION 15: Global mutable state is pervasive
================================================================================
Files: tools/__init__.py, tools/file_ops.py, tools/shell_ops.py, tools/search_ops.py
Principle: 3 (no global mutable state unless unavoidable)

Global mutable state found:
  _TOOL_CACHE           (__init__.py)  — acceptable (per-turn cache)
  _MODIFIED_FILES       (__init__.py)  — mutable set
  _TASK_REGISTRY        (__init__.py)  — mutable dict of Popen
  _TOOL_CONTEXT         (__init__.py)  — mutable AgentContext singleton
  _AGENT_RUNTIME        (__init__.py)  — None → runtime
  _MCP_MANAGER          (__init__.py)  — None → manager
  _BACKUPS              (file_ops.py)  — mutable dict
  _SYMBOL_INDEX         (search_ops.py) — mutable dict
  _REF_INDEX            (search_ops.py) — mutable dict
  _SEMANTIC_STORE       (search_ops.py) — mutable dict
  _SEMANTIC_LRU         (search_ops.py) — mutable list
  _SEM_MODEL            (search_ops.py) — None → model

Most are performance caches (indices, model), which is the "unavoidable" case.
But `_MODIFIED_FILES`, `_BACKUPS`, `_TASK_REGISTRY`, and `_TOOL_CONTEXT` are
mutable application state that could be scoped to a session object.

Suggested fix: Consider grouping session-level mutable state into a single
`SessionState` dataclass passed explicitly to tool implementations. Performance
caches can stay module-level.

VIOLATION 23: `inspect.signature` called on every dispatch
================================================================================
File: tools/__init__.py, lines ~318-322
Principle: 9 (readable over clever), Principle: 2 (explicit control flow)

  import inspect
  sig = inspect.signature(dispatch)
  if "on_output" in sig.parameters:
      result = dispatch(args, write_gate, read_gate, on_output=on_output)
  else:
      result = dispatch(args, write_gate, read_gate)

`inspect.signature` is called on every tool dispatch to check whether the tool
accepts `on_output`. This is a runtime cost (~microseconds but adds up) and a
clever/hidden mechanism. The information about which tools accept `on_output`
could be encoded at registration time.

Suggested fix: Store a flag at registration time (e.g., `_TOOL_ACCEPTS_OUTPUT:
set[str]` = {"run_shell"}) and check set membership instead.

VIOLATION 24: `verify` tool duplicates lint logic
================================================================================

     and lines ~443-458 (second lint attempt with flake8)
Principle: 14 (avoid duplicate logic)

The `verify` tool runs lint TWICE — first via `pytest test_lint.py` and then
via `flake8 --count --select=E,F,W .`. If both succeed, "Lint: passed" appears
twice in the output. The flake8 run ignores the pytest result and overwrites it.

Suggested fix: Pick one linting approach, or combine into a single lint step.
